## 2. Objetivo da Task
Implementar `/admin/agenda` para controle manual de datas/horarios e exibir profissional unico como dado somente leitura, sem CRUD.

---

## 3. Descrição Detalhada
- Criar `app/admin/agenda/page.tsx` como pagina protegida.
- Criar `ScheduleSlotGrid` para slots disponivel, bloqueado, ocupado e inativo.
- Exibir resumo do profissional unico configurado sem criar tela, action ou rota de CRUD de profissional.
- Integrar salvamento de disponibilidade com `availabilityService` por Server Action existente ou action adicionada em `adminActions`.
- Respeitar layout mobile-first do `design.md`: data/resumo acima no mobile e slots ao lado em telas maiores.

## 7. Notas / Observações
- CT-14 de ausência de rotas/actions de CRUD fica em T8 para validar superfície HTTP integrada.
- **Path real dos testes** (diverge do que está registrado em §5.1, que citava `tests/components/ScheduleSlotGrid.test.tsx`): seguindo a mesma convenção já usada por T3/T4 (`.test.tsx` colocado junto do componente — `tests/components/` não é coletado por `vitest.config.mts`), os testes ficaram em `src/features/agenda/components/ScheduleSlotGrid.test.tsx` e `src/features/agenda/components/SingleProfessionalSummary.test.tsx`. Além disso, o conteúdo literal de CT-13 (profissional único + ausência de CRUD) foi implementado no teste de `SingleProfessionalSummary` — o componente que de fato exibe o profissional — e não em `ScheduleSlotGrid` (que não tem relação com CA-10); `ScheduleSlotGrid.test.tsx` recebeu os testes extras (CT-EXT-01 a 08) que cobrem os demais critérios de aceite (§4) não detalhados em CT explícito pela task.
- **Fonte do profissional único para leitura administrativa** (decisão de causa-raiz registrada conforme pedido em §7 da task): criado `src/features/agenda/services/professionalSummary.ts` com `readConfiguredProfessionalName()`, lendo `PROFISSIONAL_UNICO_NOME` diretamente. NÃO reaproveita `resolveProfissionalUnico` de `bookingService.ts` (T2) porque essa função é privada, valida com a mensagem/regra do fluxo de reserva pública e lança `AppError("unavailable", ...)` — errado para uma tela administrativa de leitura, onde "nada configurado ainda" é estado normal (`null`), não indisponibilidade. Exportá-la de `bookingService.ts` só para reaproveitamento alargaria a superfície pública de um módulo alheio por conveniência (Regra 3/6 do Executor) — por isso a leitura foi duplicada, de forma mínima (trim + checagem de vazio), num helper próprio da feature `agenda`. Esse helper também evita um ciclo `agenda → agendamentos`: `agendamentos` já importa de `agenda` (`availabilityRepository`) para as primitivas transacionais de slot, então `agenda` importar de `agendamentos` (ex.: `appointmentValidators`) inverteria essa dependência.
- **Data padrão da Agenda**: adicionada `todayIsoDate(now?)` em `src/shared/time.ts` (mesma técnica de deslocamento de fuso que `formatInstantPtBr` já usa) para resolver "hoje" no fuso da operação (`-03:00`) quando a rota `/admin/agenda` não recebe `?data=` na query string. Sem isso, um servidor rodando em UTC mostraria o dia seguinte como "hoje" entre 21h e meia-noite no horário de Brasília — um bug de fronteira de dia que a Agenda, por ser justamente a tela de controle de datas, não pode ter.
- **Agenda manual**: a tela não usa grade fixa de horários. O admin adiciona cada horário via campo "Novo horário" + ação "Adicionar horário" (reaproveitando o rótulo literal do estado vazio do `design.md` §5.1) e alterna `liberado` nos que já existem; o salvamento envia todos os horários visíveis na grade (existentes + adicionados) via a nova Server Action `saveAvailability` (`src/features/admin/actions.ts`), seguindo exatamente o padrão `adminAction(...)` de T4.
- **Navegação para Agenda em `AdminShell`**: o item de navegação "Agenda" (`href: "/admin/agenda"`) já existia em `AdminShell.tsx` antes desta task (parte do `NAV_ITEMS` original) — nenhuma edição foi necessária nesse arquivo (ver §5.3 — apenas consultado).
- **Navegação de data**: `/admin/agenda?data=YYYY-MM-DD` (tech_spec §7: query param compartilhável) implementada com `next/form` (`Form` de `next/form`, GET com navegação client-side) em vez de `<form>` nativo — é o mecanismo que a documentação local do Next 16 (`node_modules/next/dist/docs/01-app/03-api-reference/02-components/form.md`) recomenda explicitamente para formulários que atualizam `searchParams`.
