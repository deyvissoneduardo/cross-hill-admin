## 6. Notas / Observações

**Correção estendida além do guard original**: a implementação inicial do guard em `src/firebase/admin.ts` (bloquear `NODE_ENV === "production"` + `isUsingEmulators()`) quebrou a suíte E2E emulada de T8/v1 (`playwright.config.ts`). Aquela suíte sobe LEGITIMAMENTE um terceiro servidor via `npx next start --port ${EMULATED_PORT}`, que fixa internamente `NODE_ENV=production` — comportamento inerente ao `next start`, não uma configuração deste projeto — e combina isso de propósito com `FIREBASE_AUTH_EMULATOR_HOST`/`FIRESTORE_EMULATOR_HOST` (`E2E_EMULATED_ENV`) para que CT-14/CT-22 emitam uma sessão administrativa real offline via Auth Emulator. O guard, sem distinguir esse cenário do vazamento acidental real que D-004 queria prevenir, derrubava o login em todos os 10 testes desses specs (`signInAsAdmin` preso em `/admin/login?erro=indisponivel`) — confirmado pelo QA de T2 via `git stash` isolando `src/firebase/admin.ts`.

**Correção aplicada**: o guard só lança `AppError("unavailable", ...)` quando `NODE_ENV === "production"` E `process.env.ALLOW_FIREBASE_EMULATOR_IN_PRODUCTION_BUILD !== "1"`. A flag é setada APENAS em `E2E_EMULATED_ENV` (`playwright.config.ts`), nunca presente num deploy real — a proteção original contra vazamento acidental de `*_EMULATOR_HOST` em produção permanece intacta para qualquer ambiente que não defina essa flag explicitamente. `E2E_FIREBASE_ADMIN_ENV` (usado pelo CT-21, fora do modo emulador) não foi tocado.
